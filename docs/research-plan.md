## 1. 專案概述

本專案以 vibe coding 打造一座「AI 文學獎法院」：從 20 位不同職業人設中抽出的 10 位 AI 陪審員評閱同一場次的文學獎作品，經獨立評閱、評議、計票後，由一位法官 AI 裁決名次並撰寫判決書，再與真實文學獎的決審結果及會議紀錄比對。

**研究動機**

- 文學評審是主觀且多角度的判斷，正適合檢驗多代理人（multi-agent）是否真能提供「多元觀點」，而不只是同一個模型換了名字。
- 台灣地方文學獎公開決審會議紀錄，提供了真人評審如何爭論、投票、改變心意的對照資料。
- 文學獎已開始明文禁止 AI 生成作品；本專案反過來讓 AI 擔任評審，探討 AI 的文學判斷力與盲點。

**研究問題**

1. AI 法院排出的名次，與真人評審的結果有多接近？
2. 不同職業人設的陪審員，是否真的產生不同的判斷與理由？
3. 多數決、支持比例、法官裁決三種決策方式，哪一種最接近真人結果？
4. 真人評審爭論最激烈的作品，AI 陪審團是否也分歧最大？
5. AI 陪審員提出的優缺點，與真人評審的論點重疊多少？遺漏了什麼？

**專案資訊**

## 2. 資料來源與資料集規格

資料以「場次」為單位：同一屆、同一文學獎、同一組別的得獎作品為一場，目標收集 10～15 場。因公開全文幾乎只有得獎作品，實驗任務設計為「在同一場次內排名次」，而非「單篇判斷是否得獎」，避免 AI 全部回答「該得獎」就拿到滿分。

**資料來源**

| 優先 | 文學獎 | 可取得內容 | 評審人數 | 優點 |
| --- | --- | --- | --- | --- |
| 1 | [新北市文學獎](https://literature.culture.ntpc.gov.tw/) | 決審會議紀錄 PDF、得獎作品集 | 3 | 逐位評審投票表格最清楚；有一般組與青春組 |
| 1 | [打狗鳳邑文學獎](https://tfliterature.kcg.gov.tw/) | 作品全文、評語、會議紀錄同一份 PDF | 5 | 資料最完整，評審人數最接近陪審團 |
| 2 | [臺中文學獎](https://www.culture.taichung.gov.tw/) | 決審紀錄 PDF、得獎作品集 PDF | 3 | 有逐位評審勾選表 |
| 2 | [臺南文學獎](https://culture.tainan.gov.tw/) | 決審紀錄 PDF | 3 | 部分年份採計分排序，可直接與 AI 分數比對 |

**納入標準**

- 文類：散文、新詩（篇幅短，API 成本低）；不納入小說
- 每場至少 3 篇有名次區分的得獎作品（例如首獎、優選、佳作）
- 需有可對照的決審會議紀錄
- 優先近 1～2 年的屆次（2025、2026），降低資料污染風險

**標準答案格式**（每場整理一份）

| 欄位 | 說明 |
| --- | --- |
| case\_id | 場次編號，例：NTPC-2025-散文一般組 |
| work\_id / title | 作品編號與篇名 |
| true\_rank | 真實名次（首獎=1） |
| judge\_votes | 每位真人評審在各輪的投票或分數 |
| key\_reasons | 真人評審對該篇的主要優點、缺點（摘要條列） |
| controversy | 爭議程度：低／中／高（依紀錄討論篇幅與分票判斷） |

**資料污染處理**

得獎作品與紀錄都公開在網路，模型可能讀過。每篇作品送進法院前，先問模型「是否認得這篇作品、知道作者或名次」，認得的場次剔除或另外標註。送入時移除作者姓名、獎項名稱、得獎感言與評語，只留作品本文。

## 3. 系統架構

系統模仿真實文學獎的決審會議：一個場次進來，經過兩輪陪審、三種計票，最後由法官裁決。每個場次約需 21 次模型呼叫。

&#91;embedded content: AI 文學獎法院流程 · 6 個階段\]

各階段說明：

1. **輸入**：程式讀取場次 JSON，依 order\_seed 打亂作品順序。
2. **第一輪獨立評閱**：本場次抽出的 10 位陪審員同時呼叫，每位只看得到作品與自己的人設，保證意見獨立。
3. **第二輪評議**：程式將第一輪所有理由整理成摘要，再發給每位陪審員，允許修改分數。摘要只列理由，不列分數，避免陪審員單純跟隨多數。
4. **計票**：由程式計算，不呼叫模型；三種結果的定義見第 6 節。
5. **法官裁決**：法官一次讀入全部資料，產出最終名次與判決書。
6. **對照**：與標準答案比對，所有中間結果存檔供分析。

## 4. 角色規格

陪審團共 20 位，分成「文學專業」6 位、「一般讀者」6 位、「跨界視角」8 位，讓實驗可以比較三組的判斷差異。與 Web App 一致，每個場次依組別分層隨機抽出 10 位（專業 3、一般 3、跨界 4）；抽選以場次編號為亂數種子，同一場次在所有實驗組與兩種順序中都使用同一組陪審員，確保可以比較。跨界組用與文學無關的職業經驗當閱讀鏡頭。每位有固定的關注重點，寫進人設 prompt，確保他們從不同角度閱讀。

**人設 prompt 模板**（每位陪審員共用，只替換括號內容）

```text
你是一位{職業}。{一句背景描述}。
你受邀擔任文學獎陪審員，閱讀時特別關注：{關注重點}。
請從你的職業立場出發評閱，不要試圖模仿專業文學評論家的口吻。
作品均為匭名，你不知道作者是誰，也不知道任何得獎結果。
請依指定的 JSON 格式輸出，不要輸出其他文字。
```

**法官角色**

- 定位：資深文學獎決審主席，負責綜合陪審團意見，不自己重新評分
- 可讀到：所有作品全文、兩輪分數、所有理由、三種計票結果
- 必須做到：給出最終名次、撰寫判決書與少數意見書；若結果與多數決不同，必須說明推翻理由
- 限制：不可引入陪審員沒提過的新論點作為主要依據

## 5. 資料格式規格

所有輸入輸出一律使用 JSON，程式才能自動計票與統計。模型輸出不符合格式時自動重試，最多 2 次。

**輸入：一個場次（case）**

```json
{
  "case_id": "NTPC-2025-essay-general",
  "genre": "散文",
  "works": [
    { "work_id": "W1", "text": "（作品本文，已匭名）" },
    { "work_id": "W2", "text": "..." },
    { "work_id": "W3", "text": "..." }
  ],
  "order_seed": 42
}
```

work\_id 為隨機代號，與真實名次無關；order\_seed 控制作品呈現順序，用於位置偏誤實驗。

**陪審員輸出：第一輪獨立評閱**

```json
{
  "juror_id": "J01",
  "round": 1,
  "evaluations": [
    {
      "work_id": "W1",
      "score": 8,
      "support_top3": true,
      "strengths": ["意象鮮明，結尾留白"],
      "weaknesses": ["中段節奏拖沓"],
      "one_line": "一句話總評"
    }
  ],
  "my_ranking": ["W1", "W3", "W2"]
}
```

**陪審員輸出：第二輪評議**

格式同第一輪，另加一個欄位：

```json
"changes": [
  {
    "work_id": "W2",
    "from_score": 5,
    "to_score": 7,
    "persuaded_by": "J04",
    "reason": "被指出題材在文學史上的新意後重新評估"
  }
]
```

沒有改變則為空陣列。

**法官輸出**

```json
{
  "final_ranking": ["W1", "W3", "W2"],
  "overrides_majority": false,
  "override_reason": "",
  "verdict": "判決書：首獎理由，約 300 字",
  "minority_opinion": "少數意見書：反對派最強論點，約 150 字",
  "most_contested": "W2"
}
```

**輸出紀錄**

每場次每組實驗存成一個檔案 `results/{case_id}_{condition}_{run}.json`，內含輸入、兩輪全部陪審員輸出、計票結果、法官輸出、使用的模型名稱與時間。原始紀錄不覆蓋，後續分析全部從這些檔案計算。

## 6. 決策機制

最終判決以法官裁決為準，但系統同時記錄三種自動計票結果，四者分別與真人結果比較。比較哪種方式最準，本身就是研究發現之一。

| 方式 | 計算方法 | 用途 | 限制 |
| --- | --- | --- | --- |
| ① 多數決 | 每篇獲得「支持前三」的票數，票多者名次高；同票時以平均分決定 | 最簡單、最透明的基準 | 忽略強弱差異 |
| ② 支持比例（0～1） | 支持票數 ÷ 成功評閱的陪審員數，例如 10 位全數成功時 7 票 = 0.70 | 呈現共識程度；接近 0.5 代表爭議大 | 是共識指標，不是真正的得獎機率 |
| ③ 平均分數 | 10 位陪審員分數（0～10）的平均，依此排名 | 保留強弱資訊 | 易受極端分數影響 |
| ④ 法官裁決 | 法官讀完全部分數與理由後決定名次 | 最終判決；考慮論點品質 | 可能被單一陪審員帶走 |

**規則**

- 三種自動計票皆以第二輪（評議後）分數計算；第一輪分數另存，用於分析「評議是否改變結果」。
- 不讓陪審員自報「得獎機率」。LLM 自報的機率未經校準，支持比例較可靠且易於解釋。
- 法官一定看得到①～③的結果；法官名次與①不同時，`overrides_majority` 設為 true 且必須填寫推翻理由。
- 爭議度定義：支持比例介於 0.35～0.65，或分數標準差 ≥ 2 的作品，標為「高爭議」。閾值可在第 3 週依資料分佈調整。

## 7. 實驗設計

核心問題是「多代理人法院是否優於單一 AI」，因此設計 5 個實驗組，每組跑全部場次。前 4 組為必做，第 5 組視時間加做。

| 組別 | 代號 | 做法 | 回答的問題 |
| --- | --- | --- | --- |
| 基準組 | C0 | 單一 AI、無人設，直接排名 | AI 最簡單的判斷有多準？ |
| 重複投票組 | C1 | 同一 AI、無人設，獨立跑 10 次後多數決 | 光是「人多」就有用嗎？ |
| 陪審團組 | C2 | 抽出的 10 位職業人設，第一輪後多數決 | 「人設多元」比「人多」更有用嗎？ |
| 法院組 | C3 | C2 + 第二輪評議 + 法官裁決（完整流程） | 評議與法官有沒有加分？ |
| 混合模型組（加分） | C4 | C3，但 10 位陪審員分配到 2～3 家不同模型 | 不同「腦袋」是否比不同「人設」更多元？ |

**控制變因**

- **位置偏誤**：每場次以 2 種不同 order\_seed 各跑一次，作品順序隨機打亂；分析時取平均，並檢查排在第一位的作品是否常勝出。
- **模型與溫度**：C0～C3 使用同一個模型、同一溫度設定；C1 需溫度 > 0 才會產生不同結果。
- **篇幅**：同一場次的作品一次全部送入，確保陪審員是「互相比較」。
- **匭名化**：如第 2 節，只送本文。
- **污染檢查**：正式實驗前完成，剔除被模型認出的作品。

**執行量估算**（以 12 場、每場 2 種順序計）

| 組別 | 每次執行的 API 呼叫數 | 合計呼叫數 |
| --- | --- | --- |
| C0 | 1 | 24 |
| C1 | 10 | 240 |
| C2 | 10 | 240 |
| C3 | 10 + 10 + 1 = 21 | 504 |

合計約 1,010 次呼叫；C2 的第一輪可直接重用為 C3 的第一輪，實際可再省下 240 次。全部使用 Claude Haiku 5.5 並以 Batch API 半價執行，預估總費用低於 US$3。

## 8. 評估指標

評估分「結果」與「過程」兩層：結果看名次對不對，過程看多代理人是否真的帶來多元觀點。後者是本專案最能彰顯 multi-agent 價值的部分。

**結果層：名次準不準**

| 指標 | 計算方式 | 隨機猜測基準 |
| --- | --- | --- |
| 首獎命中率 | AI 選出的第一名 = 真實首獎的場次比例 | 1 / 場次作品數（3 篇時約 0.33） |
| 排名相關（Spearman ρ） | AI 名次與真實名次的等級相關，各場取平均 | 0 |
| 順序穩定度 | 同一場次換順序後，第一名是否相同 | — |

**過程層：多元觀點是否成立**

| 指標 | 計算方式 | 回答的問題 |
| --- | --- | --- |
| 陪審員分歧度 | 每篇作品 10 個分數的標準差；比較 C1 與 C2 | 人設是否真的讓意見變多元？ |
| 論點多樣性 | 將所有 strengths / weaknesses 歸類（意象、結構、情感、題材…），計算不重複類別數 | 陪審團比單一 AI 多提出幾種論點？ |
| 論點重疊率 | 真人評審 key\_reasons 中，有多少比例也被 AI 陪審團提到 | AI 抓到了多少真人關心的點？漏了什麼？ |
| 爭議度對照 | AI 高爭議作品 vs 真人紀錄中的高爭議作品，計算吻合比例 | AI 是否察覺到「這篇有爭議」？ |
| 職業準確度 | 每位陪審員個人 my\_ranking 的 Spearman ρ | 哪種職業最接近真人評審？專業組 vs 一般組？ |
| 評議效果 | 第一輪 → 第二輪 ρ 的變化；統計 persuaded\_by 次數 | 討論讓結果變好還是變差？誰最有說服力？ |

**質化分析**

挑 2～3 個典型場次做細讀：並列真人評審紀錄、AI 判決書、少數意見書，討論 AI 的文學判斷偏好（例如是否偏愛工整、情感明確的作品），以及它看不到的東西。

論點歸類與重疊判定先由程式請 AI 初步標註，再由人工抽查至少 20% 校正，並在報告中說明標註方式。

## 9. 技術實作

以 Python 為主，程式全部以 vibe coding 方式撰寫；核心流程預估 200～400 行，不需要資料庫或伺服器。

**技術棧**

| 用途 | 工具 |
| --- | --- |
| 主程式 | Python 3.11+ |
| 模型呼叫 | Anthropic 官方 SDK（Claude Haiku 5.5，使用 Batch API） |
| 並行呼叫 | asyncio，10 位陪審員同時評閱 |
| 格式驗證 | pydantic（檢查 JSON 輸出、失敗自動重試） |
| 統計分析 | pandas、scipy（Spearman） |
| 圖表 | matplotlib |
| 法庭介面 | Streamlit |
| PDF 文字擷取 | pdfplumber（從作品集取出本文） |
| 開發工具 | Claude Code / Cursor 等 AI 程式助手 |

**成本估算方式**

先用 1 個場次跑完整 C3 流程，記錄實際用量（輸入、輸出 token），再乘以第 7 節的總呼叫數。散文 3 篇約 6,000～9,000 字，每次陪審員呼叫都要讀全部作品，輸入量是成本主因。若預算有限，可用較便宜的模型跑 C1、C2，或優先使用篇幅較短的新詩場次。模型價格會變動，以實作當下官方定價為準。

**開發紀錄**

vibe coding 過程中的重要 prompt、AI 寫錯的地方、如何驗證，統一記在 `devlog.md`，作為報告「方法論反思」的素材。

## 11. 風險、預期成果與待決事項

**風險與因應**

| 風險 | 影響 | 因應方式 |
| --- | --- | --- |
| 模型讀過得獎作品或紀錄 | 等於提前知道答案，結果失真 | 優先近年場次；實驗前做污染檢查 |
| 不同人設其實說一樣的話 | 多代理人價值不成立 | 這本身是研究發現；以 C1 vs C2 量化，並加做 C4 混合模型 |
| 每場只有 3～5 篇，樣本小 | 統計結論力道有限 | 跨年份、文類、文學獎擴充場次；報告中採描述性統計並說明限制 |
| 得獎作品品質接近，名次差異小 | AI 難以區分，準確率偏低 | 以論點重疊、爭議度等過程指標為主，不只看命中率 |
| PDF 文字擷取錯誤 | 作品本文缺字、亂碼 | 擷取後人工核對每篇開頭與結尾 |
| API 費用或額度超出預期 | 實驗無法跑完 | 第 2 週先試算；必要時縮減場次或改用較便宜模型 |
| AI 模擬的職業／年齡層是刻板印象 | 「一般讀者」意見不具代表性 | 在報告中批判討論，不將其視為真實讀者調查 |

**預期成果**

- 可執行的 AI 法院程式與原始實驗紀錄
- 10～15 個場次的標準答案資料集

## 12. 輕量研究（期末報告採用，2026-11-10 新增）

取代第 2～10 節的完整實驗。全部使用 Web App 的單篇流程與 PRD 第 5 節的單篇 schema，不需要文學獎資料集。

**12.1 法官模型比較（W0）**

- 做法見 PRD 第 11 節第零階段：5 篇測試文，陪審結果重用，分別以 Haiku 5.5 與 Sonnet 5.5 當法官。
- 產出：並列比較表（是否引用 3 位不同組別陪審員、少數意見是否具體、有無陪審員沒提過的論點、繁體中文是否正確）與法官模型的決定。

**12.2 人設多元性比較（L1，Web App 上線後）**

- 問題：10 位職業人設是否真的比「同一個 AI 跑 10 次」產生更多元的意見？
- 材料：5～10 篇文章（可沿用 W0 的 5 篇）。
- 兩組：人設組＝依 PRD 第 4 節抽出的 10 位陪審員；無人設組＝同一個模型、不帶人設的 prompt，獨立跑 10 次。兩組使用同一個模型、同一份輸出 schema。
- 指標：每篇文章 10 個分數的標準差（分歧度）；10 份輸出中不重複的 tags 數（論點種類數）；支持比例。逐篇並列，再取平均。
- 限制：Haiku 5.5 不接受自訂溫度，無人設組的差異只來自預設取樣；篇數少，只做描述性統計。
- 預估：每篇 20 次呼叫，人設組可重用既有結果；10 篇最多 200 次，全部 Haiku 約 US$0.05 以內。

**12.3 使用者研究（L1）**

- 邀請 10～20 位同學試用網站並填問卷（問卷由專案負責人設計與發放）。
- 網站提供管理者匯出投稿統計（PRD E-6）：每筆投稿的文類、字數、模組、分數統計與時間，不含文章全文、標題與 email。
- 報告呈現：使用次數、各模組勾選比例、分數分布、問卷結果。

## 13. 延後事項與已知設計問題（2026-11-10 記錄）

第 2～10 節的完整實驗延後。以下是閱讀文件時發現、尚未處理的問題，日後重啟時須先決定。

**與 Web App 規格的差異**

- 陪審員輸出 schema 不同：本文件第 5 節是整場評閱（`evaluations[]`、`support_top3`、`my_ranking`），PRD 是單篇（`score`、`would_support_award`、`comment`、`tags`）。已決定：兩種模式共用同一份人設與人設核心 prompt，只有任務段落不同；目前只實作單篇。
- 第 4 節的人設 prompt 模板缺少 `<article>` 聲明與評分校準。已決定：以 PRD 第 4 節的模板為準，研究模式另加「作品均為匿名」一句。
- 第 9 節的專案結構（`ai-literary-court/`）不採用，依 CLAUDE.md 的 `/shared`、`/research`、`/web`。
- 模型設定：Haiku 5.5 不接受自訂溫度（第 7 節「同一溫度設定」「C1 需溫度 > 0」無法照做，只能使用預設取樣並實測 C1 是否有差異）；Haiku 5.5 預設開啟思考，會計入輸出 token。已決定：陪審員關閉思考，法官保留。

**尚未決定的研究設計問題**

1. 「支持前三」（`support_top3`）在只有 3 篇的場次沒有鑑別力：每篇都在前三，多數決與支持比例會全部同票，直接影響研究問題 3。可改為「支持首獎」，或以 `my_ranking` 做 Borda 計分，並優先蒐集 4 篇以上的場次。
2. Spearman 在 3 篇時只有四種可能值；文學獎常有並列名次（佳作數名），`true_rank` 需要明訂並列的寫法。
3. C2 的計票輪次：第 6 節說三種計票皆以第二輪計算，但 C2 的定義是第一輪後多數決。建議 C2 直接重用 C3 第一輪的計票結果。
4. C0、C1 的輸出格式未定義。建議沿用場次 schema、不帶人設；C0 取 `my_ranking`，C1 取 10 次的多數決。
5. `order_seed` 寫在場次 JSON 內，但每場要跑 2 種順序。建議改為執行參數。
6. 污染檢查只靠模型自述並不可靠（說不認得不代表沒讀過）。建議加上較客觀的測試（給前半段，問作者與出處或要求續寫），結果用於標註而非直接剔除，並在報告寫明限制。
7. C4 需要其他廠商的金鑰與 SDK，與目前只用 Anthropic SDK 的決定不一致。建議不做，或以 Haiku＋Sonnet 混合代替。
8. Batch API 與兩輪流程：第二輪依賴第一輪、法官依賴第二輪，C3 須分三批依序送出，每批最長可能等待 24 小時，時程須預留。
9. Streamlit 法庭介面：已由 Web App 取代，是否仍需要待定。
10. 論點歸類、重疊率與每場的 `key_reasons` 摘要都需要人工標註與抽查，須預留工時。

**原估算（供日後參考）**：12 場、2 種順序、C2 重用為 C3 第一輪時約 770 次呼叫；全部 Haiku 5.5 並使用 Batch API 約 US$1～1.5。此數字以每字約 1.3～1.5 token 估算，未經實測。
